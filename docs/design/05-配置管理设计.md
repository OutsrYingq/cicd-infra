# 05 配置管理设计

对应实现：`deploy/envs/`、generic-service chart 的 config/sealedSecrets 能力。

## 1. 分层模型

```
最终生效值 = chart 默认值 (cicd-infra/charts/generic-service/values.yaml)
           ⊕ 环境值 (deploy/envs/<env>/<svc>..yaml)        ← 主要改动面
           ⊕ 密文 (SealedSecret，同在 envs 文件内)          ← 敏感项
```

- **chart 层**：与"所有服务都一样"的默认（探针、traefik、小资源规格）
- **环境层**：与"某服务在某环境"的差异（副本、域名、日志级别、资源、镜像 tag）
- **密文层**：加密后的敏感值，与明文配置同文件管理但物理隔离（密文泄漏无害）

任何变更走 PR：diff 可评审、历史可追溯、 revert 即回滚。

## 2. 目录与文件约定

```
deploy/
└── envs/
    ├── dev/
    │   ├── user-api.yaml      # 服务名 = 文件名（强制，CI bump 按此寻址）
    │   └── order-svc.yaml
    └── prod/
        └── user-api.yaml
```

规则：

1. 文件名 = `service` 字段 = 镜像名 = k8s 资源名前缀，**全小写**
2. 文件顶部必须带 `service` / `env` 元字段（ApplicationSet 依赖）
3. 新环境 = 新目录（`envs/staging/`…），ApplicationSet 自动纳管
4. 禁止提交明文密钥（见第 4 节）

## 3. 非敏感配置：改配置即生效链路

```
改 envs/dev/user-api.yaml 的 config.LOG_LEVEL
  → PR merge → Argo CD ≤3min 感知
  → helm 重渲染 → ConfigMap 更新
  → deployment 的 checksum/config 注解变化 → 滚动重启
  → 新 Pod 环境变量生效
```

关键实现（chart 层，03 文档 4.2）：Pod 注解注入 ConfigMap 的 sha256。没有这个机制，envFrom 的 ConfigMap 更新后旧 Pod 不会重启，出现"改了但没生效"的幽灵问题。

## 4. 敏感配置：sealed-secrets

### 4.1 原理

- 本地 `kubeseal` 用集群控制器的**公钥**加密 → 密文（SealedSecret CR）
- 密文入 Git；控制器在集群内用私钥解密 → 生成普通 Secret
- 默认 **strict scope**：密文绑定 `namespace + name`，换位置即失效，防密文挪用（唯一例外：GHCR 拉取凭证用 cluster-wide，见 4.3 / ADR-8）
- 私钥仅存在于集群（etcd + 控制器内存），GitHub 泄漏 ≠ 明文泄漏
- 集群灾难恢复需备份私钥（实现步骤文档含备份命令）

### 4.2 标准用法

```bash
# 生成：编辑明文 secret.json 后
kubeseal --format yaml < secret.json > sealed.yaml
# 把 spec.encryptedData 填进 envs/<env>/<svc>.yaml 的 sealedSecrets 段

# chart values 形态（03 文档 3 节）：
sealedSecrets:
  user-api-secret:
    encryptedData:
      db-password: AgBm...

# 应用侧引用：
secretEnv: user-api-secret        # 整包注入 envFrom
# 或 extraEnv 逐 key valueFrom
```

### 4.3 GHCR 拉取凭证（imagePullSecret）

k3s 节点拉私有镜像需要 docker-registry 类型 Secret（内含 classic PAT，`read:packages`）。**已确认方案（ADR-8）：cluster-wide sealed 密文，一份全集群复用**：

```bash
# 1. 生成明文 secret（cluster-wide 与 ns 无关，任意 ns 起草均可）
kubectl create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io \
  --docker-username=<user> \
  --docker-password=<GHCR_PULL_TOKEN> \
  -n default --dry-run=client -o json > pull.json

# 2. seal 成 cluster-wide 密文
kubeseal --scope cluster-wide --format yaml < pull.json > ghcr-pull-sealed.yaml
```

把输出中的 `encryptedData` 填进**每个服务的 values 文件**：

```yaml
imagePullSecrets: [{name: ghcr-pull}]
sealedSecrets:
  ghcr-pull:
    annotations:
      sealedsecrets.bitnami.com/cluster-wide: "true"   # ⚠️ 必须保留：控制器靠它选择解密模式
    template:
      type: kubernetes.io/dockerconfigjson   # SealedSecret 解出 docker-registry 类型 Secret
    encryptedData:
      .dockerconfigjson: AgB...              # kubeseal 输出，各文件粘贴同一份
```

PAT 轮换：重新 kubeseal 一次，脚本替换所有 envs 文件后提 PR（实现步骤阶段 7 给出循环命令）。
应急通道：目标 namespace 手工 `kubectl create secret docker-registry ghcr-pull ...`（脱离 Git 管理，仅排障用）。

## 5. 环境晋升（dev → prod）

1. 复制 `envs/dev/<svc>.yaml` → `envs/prod/<svc>.yaml`
2. 改差异项：replicas、资源、域名、日志级别、HPA；**tag 保持 CI 管理**（首次手动填当前线上版本）
3. PR → review（即晋升审批）→ merge → prod 应用创建并同步

原则：**晋升是配置动作，不是镜像动作**——prod 与 dev 跑同一个 sha 的镜像（不可变产物），差异只在配置。

## 6. 配置项速查

| 想改什么 | 改哪里 | 生效方式 |
|---|---|---|
| 环境变量（非敏感） | `config:` | merge 后自动（滚动重启） |
| 副本数 | `replicaCount:` | 自动 |
| 域名 | `ingress.host` | 自动 |
| 资源限制 | `resources:` | 自动（滚动重建） |
| 敏感配置 | `sealedSecrets:` 密文 | 自动（控制器解密后） |
| 镜像版本 | `image.tag` | 自动（**正常情况由 CI 维护，手动改 = 定点发布/回滚**） |
| chart 行为本身 | cicd-infra chart 模板 | 走 cicd-infra PR + tag 发版 |

## 7. 红线与守则

1. **明文密钥禁止入 Git**——任何环境的任何密钥，一律 sealed
2. `imageCredentials`（明文 PAT 进 values）仅允许 dev 临时验证，prod 禁用
3. sealed 密文与 namespace/name 绑定，**改名服务/环境必须重新 kubeseal**
4. 配置变更必须走 PR（deploy 仓库 main 保护），不直接 push
