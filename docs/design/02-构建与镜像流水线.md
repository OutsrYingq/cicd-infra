# 02 构建与镜像流水线设计

对应实现：`cicd-infra/.github/workflows/pipeline.yml`（可复用）、`deploy-vm.yml`（见 06 文档）。

## 1. 复用机制：Reusable Workflow

业务仓库通过 `uses` 引用本仓库的 workflow：

```yaml
jobs:
  pipeline:
    uses: OutsrYingq/cicd-infra/.github/workflows/pipeline.yml@v1
    with:
      service: user-api
    secrets: inherit
```

机制要点：

- 被引用方声明 `on: workflow_call`，定义 inputs（类型校验）与 secrets
- **执行上下文在业务仓库**（checkout 的是业务代码，`GITHUB_TOKEN` 属于业务仓库），这是"基础设施逻辑集中、构建对象分散"的关键
- `secrets: inherit` 透传组织级 secrets（如 `GITOPS_PAT`）
- 业务仓库的 workflow 文件必须放在自己的 `.github/workflows/` 下（引用的触发器写在业务仓库，被引用方不能再有触发器）

## 2. pipeline.yml 接口定义

### inputs

| 名称 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `service` | string | ✅ | - | 服务名。= 镜像名 = deploy 仓库文件名 = k8s 资源名。**必须小写**（GHCR 限制） |
| `deploy-env` | string | ❌ | `""` | 目标环境（dev/prod）。空 = 只构建不部署（如 feature 分支验证） |
| `dockerfile` | string | ❌ | `Dockerfile` | Dockerfile 路径，非根目录时指定 |
| `platforms` | string | ❌ | `linux/amd64` | 目标架构。有 ARM 节点时改 `linux/amd64,linux/arm64`（QEMU 模拟，构建变慢） |

> 测试不作为流水线输入：在 Dockerfile 的 `test` stage 内执行（ADR-9），流水线语言无关、不依赖 runner 预装工具链。

### outputs

| 名称 | 说明 |
|---|---|
| `image` | 完整镜像名，如 `ghcr.io/outsryingq/user-api` |
| `tag` | 本次构建 tag（sha 短哈希） |

### 依赖的外部 secrets（组织级）

| secret | 用途 | 定义位置 |
|---|---|---|
| `GITOPS_PAT` | deploy job 向 deploy 仓库 push | GitHub org secrets（fine-grained，仅 deploy 仓库 contents:write） |

GHCR 推送**不需要**任何 secret：用业务仓库自身的 `GITHUB_TOKEN`（见第 5 节）。

## 3. 顶层声明

```yaml
permissions:
  contents: read     # 只需读代码
  packages: write    # 推 GHCR

concurrency:
  group: pipeline-${{ inputs.service }}-${{ inputs.deploy-env || github.sha }}
  cancel-in-progress: false   # 同服务同环境的部署串行，不互相打断
```

## 4. build job 设计

步骤序列：

1. `actions/checkout@v4` — 拉业务仓库源码
2. **测试** — 在 Dockerfile `test` stage 内执行，`build` stage 依赖它：测试失败 → 编译失败 → 无镜像产出（ADR-9，模板见 `docker/go.Dockerfile`、`docker/node.Dockerfile`）
3. **meta** — 计算镜像名与 tag：
   - `image = ghcr.io/${GITHUB_REPOSITORY_OWNER,,}/${service}`（bash 小写展开，org 名可能含大写）
   - `tag = git rev-parse --short HEAD`（7 位 sha）
4. `docker/setup-qemu-action@v3` — 多架构模拟（仅 arm64 需要，保留无害）
5. `docker/setup-buildx-action@v3`
6. `docker/login-action@v3` — `ghcr.io`，`${{ github.actor }}` + `${{ secrets.GITHUB_TOKEN }}`
7. `docker/build-push-action@v6`：
   - `push: true`，`context: .`，`file: inputs.dockerfile`
   - `tags: image:tag`（仅此一个 tag，不做 latest）
   - `cache-from: type=gha` / `cache-to: type=gha,mode=max` — 层缓存挂在业务仓库的 GitHub Actions cache 上，二次构建只重建变更层

语言级缓存（go mod / npm）由 Dockerfile 模板内的 BuildKit cache mount 解决（见 `docker/` 模板），流水线不感知语言。

## 5. GHCR 关键行为与设置

| 事项 | 说明 |
|---|---|
| 认证 | `GITHUB_TOKEN` + `permissions: packages: write`，同 org 内免配置 |
| 包创建 | 首次推送自动创建包，**默认 private 且关联到源仓库** |
| 包可见性 | org 设置 → Packages → 改为 internal（org 内可见）；跨仓库 Actions 使用需在包设置中授权（或 org 级"允许 Actions 写包"） |
| 命名 | `ghcr.io/<org>/<service>`，路径必须**全小写** |
| 拉取 | k3s 节点 / 虚机需要 `imagePullSecret`（classic PAT，`read:packages`，见 05/07 文档） |

## 6. deploy job 设计（GitOps bump）

```
条件: inputs.deploy-env != ''
依赖: needs: build
环境闸门: environment: ${{ inputs.deploy-env }}   ← prod 在此挂审批人
```

步骤：

1. `actions/checkout@v4`：
   - `repository: ${{ github.repository_owner }}/deploy`
   - `token: ${{ secrets.GITOPS_PAT }}`（业务仓库的 GITHUB_TOKEN 无权跨仓库 push）
2. 安装 yq（wget 二进制到 /usr/local/bin）
3. bump + commit + push：

```bash
FILE=envs/${{ inputs.deploy-env }}/${{ inputs.service }}.yaml
[ -f "$FILE" ] || { echo "::error::deploy 仓库缺少 $FILE"; exit 1; }
yq -i '.image.tag = "${{ needs.build.outputs.tag }}"' "$FILE"
git config user.name  "ci-bot"
git config user.email "ci-bot@users.noreply.github.com"
git commit -am "deploy(${{ inputs.deploy-env }}): ${{ inputs.service }} -> ${{ needs.build.outputs.tag }}"
git push
```

设计要点：

- **CI 不直接碰集群**。部署动作 = 改 deploy 仓库一个字段，集群侧由 Argo CD 完成（见 04 文档）。kubeconfig 永不出现在 GitHub
- commit message 固定格式 `deploy(<env>): <service> -> <sha>`，deploy 仓库 git log 即发布日志
- values 文件缺失时显式报错并给出提示（新服务接入最常见的翻车点）
- environment 不存在时 GitHub 会隐式创建（无保护规则）；**prod 必须显式配置 reviewers**（见 07 文档）

## 7. 业务仓库接入模板（最终形态）

```yaml
# 业务仓库 .github/workflows/ci.yml —— 接入仅需此文件
name: CI/CD
on:
  push:
    branches: [main]                  # 合并即自动发 dev
    paths-ignore: ["**.md", "docs/**"]
  pull_request:                       # PR 只验证：测试+构建，不推镜像不部署
  workflow_dispatch:                  # 一键部署入口
    inputs:
      env:
        type: choice
        options: [dev, prod]
        description: 目标环境

jobs:
  pipeline:
    uses: OutsrYingq/cicd-infra/.github/workflows/pipeline.yml@v1
    with:
      service: user-api
      deploy-env: ${{ (github.event_name == 'push' && 'dev') || inputs.env || '' }}
    secrets: inherit
```

触发语义（由 `deploy-env` 表达式 `(push && 'dev') || inputs.env || ''` 决定）：

- pull_request → `''`：测试 + 构建验证，**不推镜像不部署**（build-push-action `push: false`）
- push main → `'dev'`：构建 → 推 GHCR → 自动部署 dev
- 手动触发选 prod → deploy job 进入 `environment: prod` → 审批 → bump → 发布

## 8. 版本引用策略

| 阶段 | 业务仓库引用 | 说明 |
|---|---|---|
| 建设期 | `@main` | 快速迭代，改完即生效 |
| 稳定期 | `@v1` | cicd-infra 发 `v1.x` tag 并移动 `v1` 指针；GitHub 对移动 tag 有解析缓存（分钟级延迟），紧急修复可发独立 tag（如 `v1.2.1`）让业务仓库显式引用 |
| 破坏性变更 | `@v2` | 双轨并行一个迭代后收敛 |

cicd-infra 仓库自身约定：main 分支保护（PR + review）、每次变更更新 CHANGELOG、tag 即发布。

## 9. 完整 workflow 设计稿

```yaml
name: Service Pipeline

on:
  workflow_call:
    inputs:
      service:
        description: 服务名（小写，=镜像名=应用名）
        required: true
        type: string
      deploy-env:
        description: 部署环境（空=只构建不部署）
        required: false
        type: string
        default: ""
      dockerfile:
        description: Dockerfile 路径
        required: false
        type: string
        default: "Dockerfile"
      platforms:
        description: 目标架构
        required: false
        type: string
        default: "linux/amd64"

permissions:
  contents: read
  packages: write

concurrency:
  group: pipeline-${{ inputs.service }}-${{ inputs.deploy-env || github.sha }}
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.image }}
      tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4

      - name: Compute image metadata
        id: meta
        run: |
          echo "image=ghcr.io/${GITHUB_REPOSITORY_OWNER,,}/${{ inputs.service }}" >> "$GITHUB_OUTPUT"
          echo "tag=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"

      - uses: docker/setup-qemu-action@v3
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: .
          file: ${{ inputs.dockerfile }}
          platforms: ${{ inputs.platforms }}
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.image }}:${{ steps.meta.outputs.tag }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    if: inputs.deploy-env != ''
    needs: build
    runs-on: ubuntu-latest
    environment: ${{ inputs.deploy-env }}
    steps:
      - uses: actions/checkout@v4
        with:
          repository: ${{ github.repository_owner }}/deploy
          token: ${{ secrets.GITOPS_PAT }}

      - name: Install yq
        run: |
          sudo wget -qO /usr/local/bin/yq https://github.com/mikefarah/yq/releases/latest/download/yq_linux_amd64
          sudo chmod +x /usr/local/bin/yq

      - name: Bump image tag in deploy repo
        run: |
          FILE="envs/${{ inputs.deploy-env }}/${{ inputs.service }}.yaml"
          if [ ! -f "$FILE" ]; then
            echo "::error::deploy 仓库缺少 $FILE（参考 envs/README.md 的示例创建）"
            exit 1
          fi
          yq -i '.image.tag = "${{ needs.build.outputs.tag }}"' "$FILE"
          git config user.name  "ci-bot"
          git config user.email "ci-bot@users.noreply.github.com"
          git commit -am "deploy(${{ inputs.deploy-env }}): ${{ inputs.service }} -> ${{ needs.build.outputs.tag }}"
          git push
```

## 10. 已知风险与对策

| 风险 | 对策 |
|---|---|
| `GITHUB_TOKEN` 推包 403 | 检查 org 对 Actions 的 packages 写策略；包已存在但未授权业务仓库时，在包设置加 Actions 写权限 |
| ARM 构建慢（QEMU） | 默认只构建 amd64；确有 arm 负载再开双架构，或后续接自托管 arm runner |
| fork PR 滥用构建资源 | PR 事件不推镜像不部署；GitHub 默认不向 fork PR 透传 secrets |
| deploy 仓库 push 冲突 | 发布频率低 + concurrency 串行，冲突概率极小；重跑即可 |
| 移动 tag 缓存延迟 | 见第 8 节版本策略 |
