# 06 虚机部署通道设计

对应实现：`cicd-infra/.github/workflows/deploy-vm.yml`、`cicd-infra/docker/compose.yaml`（模板）。

## 1. 定位

少量遗留/特殊服务跑在虚机上（docker + docker compose），不迁 k3s。此通道提供与 k3s 通道**一致的发布体验**（同一个触发入口、同样的镜像产物、同样的审批语义），不追求配置管理对等（虚机配置本地维护）。

优先级：P4，k3s 主链路稳定后实施。

## 2. 流程设计

```
业务仓库 ci.yml（同一入口）
  └─ uses: deploy-vm.yml@v1
       ├─ 计算镜像 tag（与主链路同规则：sha 短哈希）
       └─ SSH 到虚机：
            cd /opt/apps/<service>
            docker login ghcr.io（PAT read:packages）
            IMAGE_TAG=<sha> docker compose up -d --pull always
```

## 3. 虚机侧约定

目录布局（每服务固定，部署动作幂等）：

```
/opt/apps/<service>/
├── docker-compose.yml   # 来自 cicd-infra/docker/compose.yaml 模板，初始化时拷贝
└── .env                 # 本地维护：ORG / PORT / 非敏感配置
```

compose 模板（`cicd-infra/docker/compose.yaml`）：

```yaml
services:
  app:
    image: ghcr.io/${ORG:?}/${SERVICE:?}:${IMAGE_TAG:?}
    restart: unless-stopped
    ports:
      - "${PORT:-8080}:${PORT:-8080}"
    env_file: [.env]
```

- 版本通过 `IMAGE_TAG` 环境变量注入，**compose 文件本身不含版本**，模板一份通用
- 配置走 `.env`（虚机本地，不进 Git——虚机侧配置管理从简，是此通道的明确取舍）
- 前置依赖：虚机装好 docker + compose 插件、部署用户、`/opt/apps/<service>` 初始化

## 4. workflow 接口

```yaml
# deploy-vm.yml（可复用）
inputs:
  service:   必填，同主链路命名
  host:      可选，默认用组织变量 VM_HOST（多虚机时逐服务指定）
secrets（组织级，inherit 透传）:
  VM_SSH_KEY         虚机部署用户私钥
  GHCR_PULL_USER     拉取 PAT 用户名
  GHCR_PULL_TOKEN    classic PAT，read:packages
```

步骤：checkout 业务仓库取 sha → `appleboy/ssh-action@v1` 执行登录与 `compose up -d --pull always`。

## 5. 与 k3s 通道的差异清单

| 维度 | k3s 通道 | 虚机通道 |
|---|---|---|
| 发布 | 改 deploy 仓库 tag → Argo 同步 | SSH 直推 compose up |
| 配置 | Git 化 + sealed | 虚机本地 .env |
| 回滚 | git revert | 重跑 workflow 传旧 tag（或本地 IMAGE_TAG=xxx up） |
| 状态可视 | Argo UI | 无（登录虚机看） |

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| SSH key 泄漏 | 仅授权部署用户 + 限制来源 IP；key 定期轮换 |
| 虚机漂移（本地改 compose） | 模板纳管 + 变更走 cicd-infra；定期 diff |
| 并发部署互踩 | workflow `concurrency` 按 service 串行 |
