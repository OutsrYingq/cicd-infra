# 01 总体架构

## 1. 背景与目标

现状痛点：

- 每个服务各自维护一套 CI 配置，重复且水平参差
- 构建产物（镜像）没有统一规范，推送、命名、版本随意
- 配置散落在脚本、聊天记录、个人电脑里，"线上到底跑的什么"说不清
- 部署靠手工操作，无审批、无审计、无回滚

目标：建设**集中式 CI/CD 基础设施**，一次建设、N 个服务复用：

| 诉求 | 对应能力 |
|---|---|
| 构建 | 可复用流水线（reusable workflow），业务仓库一行引用 |
| 上传镜像仓库 | 统一推 GHCR，GITHUB_TOKEN 免密，规范 tag |
| 配置管理 | 环境配置 Git 化（deploy 仓库），分层合并，敏感配置 sealed-secrets 加密 |
| 一键部署 | Argo CD GitOps，CI 改一个 tag 即发布；workflow_dispatch + 环境审批 |

环境现状（选型输入）：

- 代码托管 / CI：GitHub Actions
- 部署目标：**主要 k3s**（单集群为主），少量虚机
- 镜像仓库：**GHCR**（ghcr.io）

## 2. 总体架构

```
 业务仓库 × N                    cicd-infra 仓库                   deploy 仓库（独立 Git 仓库）
┌─────────────────┐            ┌────────────────────┐            ┌────────────────────────┐
│  业务代码         │            │ .github/workflows/ │            │ envs/dev/<svc>.yaml     │
│  Dockerfile      │  uses@v1   │  ├ pipeline.yml     │  git push  │ envs/prod/<svc>.yaml    │
│  ci.yml (~15行)  │───────────▶│  └ deploy-vm.yml    │───────────▶│ argocd/applicationset   │
└─────────────────┘            │ charts/generic-svc │  (改 tag)   │ bootstrap/ (安装手册)    │
        │                       │ docker/ 语言模板    │            └───────────┬────────────┘
        │                       └────────────────────┘                        │ watch (≤3min)
        │ buildx + GITHUB_TOKEN                                             ┌────────▼─────────┐
        ▼                                                                    │  Argo CD (k3s)   │
   ghcr.io/outsryingq/<svc>:<sha> ──────────────────────────────────────────────▶ │  SealedSecrets   │
                                                                             │  generic chart   │──▶ Pod/Ingress
 虚机通道: deploy-vm.yml ──SSH──▶ docker compose pull && up -d
```

数据流（一次发布）：

1. 业务仓库 merge 到 main → 触发 `ci.yml`
2. `ci.yml` 引用 `cicd-infra/.github/workflows/pipeline.yml@v1`
3. build job：构建镜像 → 推 `ghcr.io/outsryingq/<svc>:<sha>`
4. deploy job（进入 GitHub Environment，prod 需审批）→ 用 yq 改 deploy 仓库 `envs/<env>/<svc>.yaml` 的 `image.tag` → commit + push
5. Argo CD（≤3min 或 webhook 即时）发现变化 → helm 渲染 generic-service chart → 同步到 k3s
6. 集群内 sealed-secrets 控制器解密敏感配置 → Pod 拉起

## 3. 仓库职责划分

| 仓库 | 内容 | 变更频率 | 维护者 |
|---|---|---|---|
| `cicd-infra` | 可复用 workflow、通用 Helm chart、Dockerfile 模板 | 低，按 tag 发版 | 平台 |
| `deploy` | 各环境 values、ApplicationSet、sealed secrets 密文、bootstrap | 高（每次发布/改配置） | 各服务负责人（PR） |
| 业务仓库 × N | 源码 + `ci.yml`（~15 行）+ Dockerfile | 随业务 | 业务团队 |

> 本项目目录中 `deploy/` 子目录即 deploy 仓库的骨架，**最终要作为独立 Git 仓库推送**（见实现步骤文档）。拆成独立仓库的理由：流水线代码与环境配置的权限/评审隔离——服务负责人可以提 PR 改配置，但改不了流水线本身。

业务仓库接入成本 = **1 个 workflow 文件 + deploy 仓库 1 个 values 文件**，目标 10 分钟。

## 4. 技术选型与理由

| 决策点 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 复用机制 | Reusable Workflow（`workflow_call`） | GitHub 原生，跨仓库引用，可传 inputs/secrets，最贴合"独立仓库被引用" | composite action（更细粒度，作为补充）、Jenkins Shared Library |
| 镜像认证 | `GITHUB_TOKEN` + `packages:write` | 零凭证管理，同 org 内自动可信 | PAT（仅拉取侧需要） |
| 镜像 tag | git sha 短哈希 | 不可变、可追溯到 commit、天然唯一 | semver（发版场景后续叠加）、latest（禁用） |
| 部署模型 | Argo CD GitOps（pull） | Git 即状态：改配置即生效、drift 自愈、UI 可视、CI 不持集群凭证 | CI 直跑 helm（放弃，配置变"死"文件） |
| 应用编排 | ApplicationSet（files generator） | "envs 下多一个 yaml = 多一个应用"，零手工注册 | 逐个手写 Application、app-of-apps |
| 配置渲染 | Helm 通用 chart（generic-service） | 一份 chart 服务所有无状态服务，values 差异化 | Kustomize overlay（表达力弱）、每服务独立 chart（重复） |
| 敏感配置 | sealed-secrets | 无外部依赖（vs Vault），密文可入 Git，k3s 友好 | Vault+ESO（规模化后）、SOPS+age |
| Ingress | 沿用 k3s 自带 traefik | 零额外组件 | nginx-ingress |

## 5. 关键设计决策（ADR 摘要）

### ADR-1 基础设施引用用固定 tag（@v1），不用 @main

业务仓库 `uses: OutsrYingq/cicd-infra/.github/workflows/pipeline.yml@v1`。cicd-infra 按 tag 发版，`v1` 指针随次版本前移，破坏性变更升 `v2`。避免基础设施一个 commit 打挂所有服务的流水线。
注意：GitHub 对 ref 有解析缓存，移动 tag 后最长可能有分钟级延迟；建设初期可直接用 `@main` 加快迭代，稳定后切 `@v1`。

### ADR-2 部署与配置统一收敛到 deploy 仓库（单一事实源）

集群状态 = deploy 仓库内容。发布 = 改 tag，改配置 = 改 values，回滚 = git revert。Argo CD `selfHeal` 保证集群与 Git 一致，任何手工 kubectl 改动会被纠正或暴露。

### ADR-3 prod 门禁放在 GitHub Environment，不放在 Argo CD

prod 的审批由 deploy job 的 `environment: prod`（required reviewers）承担：审批通过才会发生 tag bump，Argo CD 侧保持统一自动同步，避免两套门禁逻辑。deploy 仓库 main 分支保护（要求 PR）作为配置变更的第二道闸。

### ADR-4 镜像 tag 用 sha，不做 latest

一切引用明确版本；回滚 = 把 values 的 tag 改回旧 sha。多架构镜像 manifest 由 buildx 一次性产出（amd64 默认，按需加 arm64）。

### ADR-5 敏感配置允许进 Git，但必须 sealed

sealed-secrets 密文与特定 namespace+name 绑定（strict 模式），泄漏仓库也不等于泄漏明文，且解密私钥只在集群内。

### ADR-6 dev/prod 同集群、双 namespace 隔离（已确认）

单套 k3s，`<svc>-dev` / `<svc>-prod` 按 namespace 隔离。理由：现状最简、资源利用率高，配合 resources 限额控制爆炸半径；后续可加 ResourceQuota/LimitRange 收紧 dev。演进路径：出现第二集群时 ApplicationSet 换 clusters generator 按 env 路由，业务仓库与 values 零改动。

### ADR-7 Ingress HTTP 起步，预留 TLS 接入点（已确认）

`ingress.tls.enabled` 默认 false，内网/IP 直连即可。出现对外或合规需求时接入 cert-manager 自动签发，values 只需开 tls，chart 不动。

### ADR-8 GHCR 拉取凭证用 cluster-wide sealed 密文（已确认）

`kubeseal --scope cluster-wide` 生成一份密文，粘贴到各服务 values 复用；PAT 轮换用脚本一次替换全部文件。牺牲 namespace 绑定性换运维简单——该 Secret 仅含只读 PAT，风险可接受。应用自身密文仍用默认 strict scope。

### ADR-9 测试进 Dockerfile（已确认）

多阶段 Dockerfile 增加 `test` stage，`build` stage 依赖它：测试不过、编译不过、镜像不产。消除 runner 工具链版本漂移，流水线彻底语言无关。

### ADR-10 cicd-infra 仓库必须 public（个人账户硬约束）

GitHub 规则：私有仓库的可复用 workflow **只能被同仓库调用**；跨仓库 `uses` 要求 callee 公开或同组织。个人账户无组织，故 cicd-infra 设为 **public**（模板+文档，无私密信息，公开前经敏感信息扫描），deploy 仓库保持 **private**（含环境配置与密文）。若未来迁移组织，可改回私有，引用方式不变。

## 6. 阶段演进路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| P1 | cicd-infra 骨架 + pipeline.yml + generic-service chart | 直接实施 |
| P2 | deploy 仓库 + Argo CD + sealed-secrets + 试点服务全链路 | 直接实施 |
| P3 | prod 环境审批 + 分支保护 | 直接实施 |
| P4 | 虚机部署通道 deploy-vm.yml | 按需 |
| P5 | 推广：存量服务批量迁移 | 试点稳定后 |

（本方案跳过"先直跑 helm 的 MVP 阶段"，直接落 Argo CD，理由见 04 文档第 1 节。）
