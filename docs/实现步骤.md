# 实现步骤（分阶段落地手册)

> 按阶段执行，每阶段末尾有**验收标准**，全部通过再进下一阶段。
> 示例服务 `user-api` 替换为试点服务名；仓库地址已按个人账户 OutsrYingq 写定。

## 阶段 0：准备与前置检查

1. k3s 集群可用，本地 `kubectl` 已配好 context，且 metrics-server 正常（HPA 前提，k3s 默认内置）：
   ```bash
   kubectl get nodes && kubectl top nodes
   ```
2. 本地工具：`helm`（≥3.14）、`kubeseal`、`yq`、`git`
3. GitHub：对 org 有 Settings 权限（建 org secrets / environments / 包策略）
4. DNS 可控（可选）：`*.dev.example.com` 指向 k3s 节点，用于 ingress 访问验证
5. 确定试点服务 `user-api`（选一个简单、无状态、有 `/healthz` 或可快速加的服务）

**验收**：上述命令/权限全部 OK。

## 阶段 2：deploy 仓库 + Argo CD

1. 把 `deploy/` 目录推成独立仓库 `OutsrYingq/deploy`：
   ```bash
   cd deploy
   git init && git checkout -b main
   git add .    # .gitignore 已兜底屏蔽凭证类过程文件（pull.json/私钥备份等）
   git commit -m "init: deploy repo (envs + applicationset + bootstrap)"
   git remote add origin https://github.com/OutsrYingq/deploy.git
   git push -u origin main
   ```
2. 安装 Argo CD 与 sealed-secrets（**固定版本号**，命令见 `deploy/bootstrap/README.md`），拿到 admin 初始密码，UI 能登录
3. **私有仓库必须**：为 Argo CD 配置只读 Git 凭证（deploy 与 cicd-infra 各一个 Secret，命令见 bootstrap/README 第 3 节），UI Settings → Repositories 显示 Connected
4. **替换占位符**：`deploy/argocd/applicationset.yaml` 中两处 `OutsrYingq`（cicd-infra 与 deploy 的 repoURL）
5. 应用 ApplicationSet：
   ```bash
   kubectl apply -f deploy/argocd/applicationset.yaml
   ```
6. main 分支保护：要求 PR + 1 review（此阶段先配上，后面所有变更都走 PR）

**验收**：
- [ ] `kubectl -n argocd get pods` 全部 Running
- [ ] Argo CD UI → Applications 目前为空但 ApplicationSet `services` 存在且无报错
- [ ] `kubeseal --fetch-cert` 能取到公钥（sealed-secrets 就绪）
- [ ] Argo CD UI → Settings → Repositories：deploy 与 cicd-infra 均 Connected（私有仓库场景）
- [ ] **备份 sealed-secrets 私钥**并妥善保存（丢失 = 所有密文重做）：
  ```bash
  kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml > sealed-secrets-key-backup.yaml
  ```
  > ⚠️ 该文件含解密私钥，**严禁提交到任何 Git 仓库**——存密码管理器或离线介质，并从工作目录移走

## 阶段 3：凭证与环境保护

> 个人账户没有组织级 secrets：以下 secret 配置在**使用它的业务仓库** Settings → Secrets → Actions（repository secrets），`secrets: inherit` 会透传给可复用 workflow。

1. 创建 `GITOPS_PAT`（fine-grained）：仅 `OutsrYingq/deploy` 仓库，权限 `Contents: Read and Write`，过期 90 天 → 存入 **org secrets**
2. 创建 `GHCR_PULL_USER` / `GHCR_PULL_TOKEN`（classic PAT，仅 `read:packages`）→ 存入 org secrets
3. GitHub org → Environments：
   - `dev`：无需规则
   - `prod`：Required reviewers（≥2 人）
4. org → Packages 策略：允许成员推包、Actions 写包，包默认 internal

**验收**：
- [ ] org secrets 列表包含 `GITOPS_PAT`、`GHCR_PULL_USER`、`GHCR_PULL_TOKEN`（值不可见属正常）
- [ ] Environments 页面能看到 `dev`、`prod`，prod 有审批人

## 阶段 4：试点服务接入（目标 10 分钟）

业务仓库（`user-api`）：

1. 根目录保证有可用 `Dockerfile`（参考 `cicd-infra/docker/go.Dockerfile` / `node.Dockerfile`；**模板内含 test stage，测试不过构建不过**；确保暴露端口与实现 `/healthz`）
2. 新建 `.github/workflows/ci.yml`：
   ```yaml
   name: CI/CD
   on:
     push:
       branches: [main]                  # 合并即自动发 dev
       paths-ignore: ["**.md", "docs/**"]
     pull_request:                       # PR 只验证：测试+构建，不推镜像不部署
     workflow_dispatch:                  # 一键部署入口
       inputs:
         env:
           type: choice
           options: [dev, prod]
   jobs:
     pipeline:
       uses: OutsrYingq/cicd-infra/.github/workflows/pipeline.yml@main   # 稳定后改 @v1
       with:
         service: user-api
         deploy-env: ${{ (github.event_name == 'push' && 'dev') || inputs.env || '' }}
       secrets: inherit
   ```

deploy 仓库：

3. 新建 `envs/dev/user-api.yaml`（示例见 `envs/README.md`），确认顶部 `service: user-api`、`env: dev`，`image.tag` 随意（马上会被 CI 覆盖）
4. GHCR 拉取凭证（首次）：按 05 文档 4.3 生成 **cluster-wide** sealed 密文填入 values（命令见 `deploy/bootstrap/README.md` 第 4 节），并设 `imagePullSecrets: [{name: ghcr-pull}]`

触发首次发布：

5. 业务仓库随便推一个 commit 到 main → Actions 观察 build → deploy 两个 job 变绿
6. **处理首次包权限**：首次推送生成的包若不可拉取，到包设置确认 internal + Actions 权限
7. 观察 Argo CD：`user-api-dev` 应用出现 → Syncing → Healthy

**验收**：
- [ ] `ghcr.io/outsryingq/user-api:<sha>` 镜像存在
- [ ] `kubectl -n user-api-dev get pods` Running，`kubectl logs` 是新版本
- [ ] `curl http://<ingress-host>/healthz`（DNS/hosts 指向节点后）返回 200
- [ ] deploy 仓库出现 ci-bot 的 `deploy(dev): user-api -> <sha>` commit

## 阶段 5：全链路验证（含回滚演练）

逐项执行并记录：

1. **改配置即生效**：PR 改 `config.LOG_LEVEL=debug` → merge → ≤3min 内 Pod 滚动重启且环境变量更新
2. **一键部署 prod**：手动 dispatch 选 `prod` → GitHub 弹审批 → 批准 → `user-api-prod` 应用同步成功
3. **回滚演练**：在 deploy 仓库 revert 最后一个 bump commit → dev 应用自动回到旧 sha
4. **drift 自愈**：手工 `kubectl -n user-api-dev scale deploy --replicas=5` → selfHeal 打回 1
5. **失败路径**：故意在业务仓库推一个构建失败的 commit → 流水线红、镜像不更新、集群无变化

**验收**：以上 5 项全部符合预期。任何一项不符合，先排查（见下方排障表）再继续。

## 阶段 7：存量迁移与治理

1. **每个服务的迁移 checklist**（重复执行，10 分钟/服务）：
   - [ ] 业务仓库：加 `ci.yml`（改 `service` 名与 `test-cmd`）
   - [ ] deploy 仓库：加 `envs/dev/<svc>.yaml`（元字段 + 端口 + 域名 + config）
   - [ ] 首次构建：推 commit 或手动 dispatch
   - [ ] 验证 Pod/Ingress/日志，业务流量切流
   - [ ] 旧部署方式下线
2. 治理约定：
   - cicd-infra 变更走 PR + CHANGELOG，tag 发版
   - 新服务上线必须同时具备 ci.yml + envs 文件（纳入仓库模板/规范）
   - 每季度轮换 `GITOPS_PAT`；每半年轮换 `GHCR_PULL_TOKEN`（同步重新 kubeseal）

## 排障速查

| 症状 | 原因 | 处理 |
|---|---|---|
| build job 推镜像 403 | GITHUB_TOKEN 无包权限 / 包未授权业务仓库 | 检查 workflow `permissions`；包设置加 Actions 写权限 |
| deploy job 卡在 "Waiting for a runner"/无反应 | `environment` 配置了审批 | 属预期，去 GitHub 页面批准 |
| deploy job 报缺 `envs/.../xx.yaml` | 新服务没建 values | 按 `_example.yaml` 创建 |
| Argo 应用一直不存在 | values 文件缺 `service`/`env` 元字段 | 补齐顶部两个字段 |
| Argo 同步报 helm 模板错误 | values 类型/字段写错 | UI 看 error；本地 `helm template ... -f envs/dev/xx.yaml` 复现 |
| Pod ImagePullBackOff | 包私有且无 pull secret / PAT 失效 | 配置 `imagePullSecrets`；或 sealed 的 ghcr-pull 重做 |
| ImagePullBackOff 几秒后自愈 | SealedSecret 解密时序 | 无需处理（预期抖动） |
| 改了 config 没生效 | 未满 3min 刷新 / 确认走了 PR merge | 等 refresh；UI 手动 Refresh；检查 checksum 注解存在 |
| 手工 scale 后被打回 | selfHeal | 属设计行为；临时扩容改 values 或暂停 selfHeal |
| UI 手动 Rollback 后又跳回去 | selfHeal 以 Git 为准 | **回滚必须 git revert**（04 文档第 6 节） |
| 业务仓库 uses 报 workflow not found | 引用 ref 不存在 / 仓库私有不可见 | 确认 tag 拼写；org 内可见性；tag 移动缓存等几分钟 |
| PR 触发的构建没推镜像 | 设计行为：PR 只验证不产出 | 合并到 main 后自动发布 |
| HPA 不动作 | metrics-server 缺失 | `kubectl top nodes` 自检并开启 |
